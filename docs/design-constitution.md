# FEM Design Constitution

Версия: 1.0  
Дата: 2026-07-23  
Статус: обязательная основа frontend и design-system

## 1. Назначение

Этот документ фиксирует устойчивые правила интерфейса FEM. Макеты могут меняться, но реализация не
должна превращаться в набор несвязанных страниц. Любое визуальное решение проходит через токены,
компонентный API, доступность и проверяемые состояния.

При конфликте приоритет следующий:

1. Безопасность, корректность данных и доступность.
2. Утверждённый пользовательский сценарий и API-контракт.
3. Этот документ и design tokens.
4. Макет конкретного экрана.
5. Локальное удобство реализации.

## 2. Основные принципы

### 2.1. Спортивные данные важнее декора

Результаты, календарь, рейтинг, статусы публикации и источник данных должны читаться без
дополнительного взаимодействия. Декоративная графика не конкурирует с официальной информацией.

### 2.2. Один язык визуальных решений

Одинаковые действия выглядят и ведут себя одинаково во всех модулях. Новая вариация компонента
добавляется только при наличии нового смысла или поведения, а не ради отличия страницы.

### 2.3. Progressive disclosure

Первый уровень показывает главное. Технические детали, вторичные фильтры и редкие действия
раскрываются по запросу, но не скрывают обязательные статусы и последствия операций.

### 2.4. Состояние всегда явно

Каждый экран и компонент проектируются минимум для:

- загрузки;
- пустого результата;
- частичных данных;
- ошибки с безопасным `requestId`;
- отсутствующего перевода;
- недоступного действия;
- успешного действия;
- конфликта версии;
- длинного текста и максимального реального объёма данных.

### 2.5. Public и Admin — разные контуры

Публичный интерфейс оптимизирован для поиска и чтения опубликованных данных. Admin-интерфейс
оптимизирован для точности, проверки, аудита и восстановления после ошибки. Общая визуальная база
разрешена, общие предположения о доступе — нет.

## 3. Система токенов

Токены имеют три уровня:

| Уровень   | Пример                                | Кто использует                   |
| --------- | ------------------------------------- | -------------------------------- |
| Primitive | `primitive.color.blue.600`            | Только semantic/component tokens |
| Semantic  | `semantic.color.text.primary`         | Большинство интерфейсного CSS    |
| Component | `component.button.primary.background` | Конкретный reusable component    |

Правила:

- исходник находится в `tokens/**/*.json`;
- формат — DTCG с `$value`, `$type`, `$description`;
- alias предпочтительнее копирования значения;
- приложение не использует hex, случайные px и raw primitive tokens;
- темы меняют semantic layer, а не component markup;
- изменение или удаление публичного token name считается изменением API design-system;
- `tokens/build/` генерируется Style Dictionary и не редактируется вручную.

## 4. Цвет

Базовое направление: спокойный глубокий navy для доверия и официальности, яркий blue для
интерактивности, нейтральные поверхности и отдельные feedback-палитры.

Цвет не является единственным носителем смысла. Статус дублируется текстом, иконкой или формой.

Минимальные требования:

- обычный текст: контраст не ниже 4.5:1;
- крупный текст и крупные UI-объекты: не ниже 3:1;
- focus indicator: не ниже 3:1 относительно соседних цветов;
- disabled-состояние не используется для информации, которую пользователь обязан прочитать;
- статусные background/text пары проверяются вместе в каждой теме.

## 5. Типографика

Основной стек задаётся токеном `semantic.font.family.body`. До отдельного бренд-решения используется
Inter с безопасным fallback.

Иерархия:

- `display` — только ключевой первый экран;
- `heading-lg` — заголовок страницы;
- `heading-md` — крупный раздел;
- `heading-sm` — карточка или подраздел;
- `body`, `body-sm`, `caption` — содержание, вспомогательный текст и метаданные.

Правила:

- основной текст не меньше 16 px;
- строка длинного текста ограничена приблизительно 65–75 символами;
- uppercase не применяется к длинным подписям;
- числовые таблицы используют одинаковое выравнивание и tabular numerals;
- визуальный размер не подменяет семантический HTML heading level;
- интерфейс остаётся работоспособным при 200% zoom и увеличении системного шрифта.

## 6. Пространство, сетка и контейнеры

Базовая шкала кратна 4 px. Семантические интервалы находятся в `semantic.space`.

- максимальная ширина основного контента: `semantic.layout.content-max`;
- максимальная ширина текста: `semantic.layout.text-max`;
- desktop-сетка: 12 колонок;
- tablet-сетка: 8 колонок;
- mobile-сетка: 4 колонки;
- внешние поля страницы не меньше 16 px на узком экране;
- вертикальный rhythm формируется токенами, а не случайными margin.

Breakpoint вводится по моменту, когда содержимое перестаёт работать, а не под конкретную модель
телефона. Компонент по возможности реагирует на собственный container, страница — на viewport.

## 7. Формы и действия

- один экран имеет одно визуально главное действие;
- label существует всегда и не заменяется placeholder;
- ошибка показывается рядом с полем и в итоговом summary для длинной формы;
- введённые корректные данные не теряются после ошибки;
- destructive action требует ясного названия объекта и последствий;
- pending-состояние предотвращает повторную отправку, но не скрывает результат;
- conflict UI показывает текущую версию и предлагает безопасно сравнить изменения;
- touch target по умолчанию не меньше `semantic.layout.touch-target`.

## 8. Таблицы и плотные данные

Таблица применяется для сравнения строк по одинаковым колонкам. Карточки не заменяют таблицу, если
сравнение является основной задачей.

Обязательные свойства:

- видимый заголовок и доступное описание;
- семантические `table`, `th`, `scope`;
- сортировка отражена текстом и `aria-sort`;
- фильтры можно сбросить;
- пагинация не теряет контекст;
- sticky header не перекрывает focus;
- числа выровнены по правому краю, текст — по началу строки;
- на узком экране выбирается scroll, priority columns или отдельное представление; строки не
  превращаются автоматически в карточки без проверки сценария;
- состояние «нет данных» отличается от «фильтр ничего не нашёл».

## 9. Навигация

- активный раздел определяется не только цветом;
- browser Back/Forward сохраняет ожидаемое состояние;
- фильтры, сортировка и страница кодируются в URL там, где результат должен быть доступен по ссылке;
- breadcrumb показывает положение, но не заменяет заголовок;
- ссылка используется для перехода, кнопка — для действия;
- после modal/route transition фокус перемещается предсказуемо.

## 10. Изображения, иконки и документы

- контентное изображение имеет осмысленный `alt`, декоративное — пустой `alt`;
- aspect ratio резервируется до загрузки;
- crop не должен обрезать лицо, логотип или важный спортивный контекст;
- иконка не заменяет текст для редкого или критического действия;
- PDF и скачиваемые документы показывают тип, размер и язык, если известны;
- favicon, логотип и официальная символика не перекрашиваются случайным CSS filter.

## 11. Motion

Анимация объясняет изменение состояния, а не задерживает работу.

- длительности берутся из `semantic.motion.duration`;
- layout-анимации не должны вызывать потерю фокуса;
- infinite animation не используется для обычной загрузки;
- `prefers-reduced-motion: reduce` отключает несущественное движение;
- skeleton не показывается мгновенно при очень короткой загрузке, чтобы избежать мерцания.

## 12. Доступность

Целевой уровень — WCAG 2.2 AA для публичного сайта и Admin.

Release не проходит без:

- полной клавиатурной навигации;
- видимого `:focus-visible`;
- корректного имени каждого control;
- правильного порядка заголовков;
- live-region только для действительно динамических сообщений;
- доступной ошибки и восстановления;
- теста 200% zoom;
- проверки light/dark, high-contrast и reduced-motion сценариев;
- ручной проверки экранным диктором для критических flows.

## 13. Internationalization

- строки не собираются конкатенацией;
- UI выдерживает увеличение текста минимум на 30%;
- даты, числа и имена форматируются locale-aware;
- язык документа и отдельных фрагментов размечается;
- отсутствие перевода следует утверждённой fallback policy и не маскируется пустой строкой;
- CSS использует logical properties, чтобы не закрывать будущую поддержку RTL.

## 14. Definition of Done компонента

Компонент готов, когда:

1. Назначение и границы API понятны.
2. Использованы semantic/component tokens.
3. Реализованы допустимые состояния.
4. Keyboard и focus поведение проверены.
5. Light/dark и responsive состояния покрыты.
6. Stylelint и типы проходят.
7. Visual regression добавлен или обновлён после review.
8. Нет связи с закрытыми Admin-данными в публичном контуре.
9. Документация объясняет исключения и сложные ограничения.
