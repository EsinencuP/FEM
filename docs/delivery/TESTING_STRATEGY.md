# Стратегия тестирования FEM

Версия: 1.0  
Дата: 2026-07-23  
Статус: обязательный план для разработки и приёмки

## 1. Цель

Цель тестирования — подтвердить, что публичный сайт, административная панель,
backend, база данных и интеграционные процессы работают как единая система,
не раскрывают закрытые данные и сохраняют корректность официальной спортивной
информации.

Стратегия применяется ко всем изменениям после текущего Database v1 baseline.
Тестирование считается частью разработки, а не отдельным финальным этапом.

## 2. Текущая проверенная основа

В репозитории уже предусмотрены:

- строгая TypeScript-проверка;
- ESLint и production build;
- unit-тесты конфигурации, health service и Zod validation pipe;
- E2E-проверка `GET /api/health` с реальным PostgreSQL;
- отдельные PostgreSQL constraint tests;
- применение reviewed Prisma migrations в CI;
- повторяемый demo seed;
- CI с временной PostgreSQL 16.

Эта основа сохраняется. Новые модули не должны снижать существующий уровень
проверок.

## 3. Принципы

1. Backend является источником бизнес-правил и проверки доступа.
2. Критические правила проверяются ниже уровня UI.
3. Public, Admin, Integration и Internal API тестируются как разные контуры.
4. Каждый исправленный дефект получает regression test, если это технически
   возможно.
5. Тесты не используют production-базу и реальные секреты.
6. Персональные данные в test/staging обезличиваются.
7. Нестабильный тест не отключается молча: он исправляется либо помещается в
   quarantine с владельцем и сроком устранения.
8. Успешный happy path недостаточен: обязательны проверки ошибок, повторов,
   конфликтов версий, отсутствия прав и частичных сбоев.

## 4. Окружения

| Окружение     | Назначение               | Данные                                  | Автоматические проверки           |
| ------------- | ------------------------ | --------------------------------------- | --------------------------------- |
| `development` | Локальная разработка     | Fictional demo data                     | Unit, integration, выборочные E2E |
| `test`        | CI                       | Временная БД на каждый pipeline         | Полный quality gate               |
| `staging`     | Системная проверка и UAT | Обезличенный набор, близкий к реальному | Smoke, E2E, performance, security |
| `production`  | Рабочая система          | Официальные данные                      | Безопасный smoke и мониторинг     |

Базы, файловые хранилища, ключи, очереди и webhook-адреса окружений не
пересекаются.

## 5. Уровни тестирования

### 5.1. Статические проверки

Для каждого pull request обязательны:

- форматирование;
- lint;
- TypeScript strict typecheck;
- Prisma validate и generate;
- проверка OpenAPI;
- проверка миграций;
- dependency и secret scanning;
- production build frontend и backend.

Ошибка любой обязательной проверки блокирует merge.

### 5.2. Unit-тесты

Unit-тестами покрываются:

- преобразование DTO;
- нормализация идентификаторов;
- статусы и переходы состояний;
- публикационные правила;
- правила видимости полей;
- расчётные функции после утверждения формулы рейтинга;
- идемпотентность;
- формирование безопасных ошибок;
- правила импорта одной строки;
- подпись и проверка webhook;
- разрешения административных и технических субъектов.

Для критической доменной логики нужны положительные, отрицательные и граничные
сценарии. Процент покрытия используется как индикатор, но не заменяет проверку
бизнес-правил.

### 5.3. Database и migration tests

Проверяются:

- уникальные и внешние ключи;
- обязательные поля;
- допустимые статусы;
- исторические связи;
- запрет разрушения опубликованных результатов;
- сохранение внешних идентификаторов после архивирования;
- индексы ключевых списков и фильтров;
- применение миграций к пустой базе;
- обновление копии предыдущей схемы;
- повторяемость seed;
- безопасный rollback-план для каждой production-миграции.

Destructive migration без отдельного плана переноса данных и подтверждения
запрещена.

### 5.4. API integration tests

Каждый маршрут проверяется на:

- корректный HTTP-метод и статус;
- схему запроса и ответа;
- обязательные и граничные значения;
- пагинацию, сортировку и фильтры;
- неизвестные и архивные ID;
- отсутствие закрытых полей;
- авторизацию и права;
- `requestId/correlationId`;
- конфликт версии `409`;
- идемпотентный повтор;
- rate limit `429`;
- безопасный формат ошибок;
- отсутствие stack trace, SQL, секретов и внутренних путей.

OpenAPI contract является машинно проверяемым договором между frontend и
backend. Несовместимое изменение требует новой версии либо согласованной
миграции клиента.

### 5.5. Contract tests frontend/backend

Frontend CI должен проверять:

- соответствие используемых типов утверждённой OpenAPI-схеме;
- отсутствие обращения к неописанным маршрутам;
- обработку всех документированных кодов ошибок;
- поведение при пустом списке, загрузке, частичной ошибке и недоступности API;
- корректное отображение локализованных значений;
- передачу версии записи и idempotency key там, где они обязательны.

До готовности backend frontend работает через зафиксированный mock server,
сгенерированный из той же OpenAPI-схемы.

### 5.6. Component и UI tests

Проверяются:

- поля, таблицы, фильтры и пагинация;
- формы и сообщения валидации;
- loading, empty, error и success states;
- модальные подтверждения критических действий;
- сохранение несохранённых изменений;
- конфликт параллельного редактирования;
- адаптивное поведение;
- клавиатурная навигация и видимый focus;
- языковые версии и длинный текст;
- корректное отображение изображений и документов.

Snapshot tests не должны быть единственным подтверждением корректности UI.

### 5.7. End-to-end tests

Минимальный обязательный набор:

1. Посетитель открывает опубликованную новость, соревнование и результаты.
2. Черновик недоступен через Public API и прямой URL.
3. Поиск возвращает только опубликованные разрешённые поля.
4. Администратор входит с 2FA и завершает сессию.
5. Администратор создаёт черновик, просматривает preview и публикует его.
6. Второй администратор получает конфликт при сохранении устаревшей версии.
7. Изменение результата создаёт запись аудита.
8. Повтор критического запроса с тем же idempotency key не создаёт дубль.
9. Импорт проходит preview, показывает ошибки строк и применяет только
   разрешённые изменения.
10. Большой экспорт выполняется в фоне, а ссылка прекращает действие.
11. Неуспешный webhook повторяется и не отменяет основную публикацию.
12. Архивирование не разрушает исторические результаты.
13. Переключение языка сохраняет эквивалентную сущность либо применяет
    утверждённое правило отсутствующего перевода.
14. Пользователь без сессии не получает доступ к Admin API.

Критические E2E выполняются в CI или staging перед релизом.

### 5.8. Security tests

Обязательны:

- проверка обхода авторизации и IDOR;
- CSRF, CORS и security headers;
- brute-force protection и session revocation;
- cookie flags `Secure`, `HttpOnly` и допустимый `SameSite`;
- загрузка файла с неверным MIME, расширением, размером и содержимым;
- инъекции в фильтры, поиск и импорт;
- XSS в контенте и метаданных;
- отсутствие секретов в frontend bundle, логах и API;
- ограничение публичных полей allowlist-моделью;
- отзыв integration key;
- проверка подписи webhook и защиты от replay;
- dependency, container и secret scanning.

Перед production проводится независимая ручная проверка критических маршрутов.

### 5.9. Performance и resilience

Нагрузочный профиль утверждается до замера и содержит:

- объём опубликованных сущностей;
- число одновременных посетителей;
- число администраторов;
- размер таблиц результатов;
- частоту поиска;
- размер импорта и экспорта;
- долю кешированных запросов.

Проверяются:

- p50, p95 и p99 API latency;
- frontend Core Web Vitals;
- время тяжёлых административных списков;
- отсутствие N+1 и неограниченных выборок;
- очередь фоновых задач;
- поведение при недоступности поиска, webhook и файлового сервиса;
- тайм-ауты и ограниченные повторы;
- восстановление после перезапуска worker;
- отсутствие дублей после повторной обработки задачи.

### 5.10. Accessibility, compatibility и SEO

Публичный frontend проверяется на:

- WCAG 2.2 AA;
- клавиатуру и screen reader для основных сценариев;
- контраст, focus, labels, headings и alt text;
- последние две стабильные версии Chrome, Edge, Firefox и Safari;
- iOS Safari и Android Chrome;
- ширины 320, 768, 1024 и 1440 px;
- корректные title, description, canonical, hreflang, sitemap и robots;
- исключение preview, черновиков и закрытых документов из индексации.

Автоматическая accessibility-проверка дополняется ручной, а не заменяет её.

### 5.11. Import, migration и data quality

До переноса официальных данных выполняются:

- профилирование исходников;
- отчёт о пустых значениях и форматах;
- поиск дублей;
- сопоставление справочников;
- dry run;
- контрольные суммы и число строк;
- отчёт `created/updated/skipped/conflict/failed`;
- выборочная ручная сверка;
- повторный запуск того же пакета;
- rollback rehearsal;
- сверка опубликованных результатов и рейтингов с утверждённым источником.

Ни одна неоднозначность не исправляется скрыто. Она попадает в conflict report.

## 6. Матрица критичности

| Уровень  | Пример                                                        | Реакция                                      |
| -------- | ------------------------------------------------------------- | -------------------------------------------- |
| Blocker  | Потеря данных, компрометация секрета, production недоступен   | Немедленная остановка релиза                 |
| Critical | Обход прав, черновик публичен, неверный официальный результат | Релиз запрещён                               |
| Major    | Не работает основной сценарий без безопасного обхода          | Исправить до релиза либо формально перенести |
| Minor    | Локальный UI-дефект без потери функции                        | Может войти в backlog                        |
| Trivial  | Косметическое отклонение                                      | Приоритет определяется владельцем продукта   |

## 7. Quality gates

### Pull request

- статические проверки зелёные;
- unit/integration tests зелёные;
- новые маршруты отражены в OpenAPI;
- новые бизнес-правила имеют тесты;
- migration reviewed;
- нет секретов и случайных production credentials.

### Staging candidate

- E2E critical path зелёный;
- migration rehearsal пройден;
- security и performance smoke пройдены;
- frontend/backend contract совместим;
- нет открытых Blocker/Critical;
- release notes и rollback plan подготовлены.

### Production release

- критерии из `ACCEPTANCE_CRITERIA.md` подтверждены;
- UAT подписан ответственным FEM;
- backup и restore rehearsal подтверждены;
- мониторинг и alerts включены;
- назначены ответственные за релиз и rollback;
- production secrets и origins проверены.

## 8. Тестовые артефакты

Для каждого релизного кандидата сохраняются:

- версия frontend и backend;
- commit SHA;
- версия схемы БД;
- OpenAPI snapshot;
- результаты CI;
- E2E-отчёт;
- migration report;
- security и performance summary;
- UAT checklist;
- перечень известных ограничений;
- решение о выпуске.

## 9. Ответственность

| Область                           | Исполнитель               | Принимает                 |
| --------------------------------- | ------------------------- | ------------------------- |
| Unit, integration, migrations     | Разработчик backend       | Технический ответственный |
| Component, accessibility, browser | Разработчик frontend      | Технический ответственный |
| E2E и regression                  | Разработка/QA             | Технический ответственный |
| Корректность официальных данных   | FEM domain owner          | FEM                       |
| Security release gate             | Технический ответственный | Владелец системы          |
| UAT                               | Представитель FEM         | Владелец продукта         |

Если отдельного QA нет, роль выполняется разработчиком, но UAT официальных
данных остаётся за FEM.
