# FEM — DB-first план demo-MVP

Версия: 3.0  
Дата: 2026-07-24  
Статус: основной исполняемый план

> Фактическая совместимость: backend уже содержит защищённый Admin API и
> отдельный published-only Public API. Новый demo scope не требует удаления
> существующего Public API: он остаётся regression-tested техническим активом,
> но не расширяется и не используется demo-web. Актуальные результаты
> проверок находятся в `docs/delivery/CURRENT_QUALITY_STATUS.md`.

## 1. Главная цель

Подготовить существующую базу данных и backend к подключению frontend, затем
собрать минимальный рабочий интерфейс, который демонстрирует систему учёта
Национальной федерации конного спорта Молдовы.

Demo-MVP должен показать заказчику:

- единый реестр спортсменов;
- единый реестр лошадей;
- поиск, фильтрацию, сортировку и пагинацию таблиц;
- карточку спортсмена и карточку лошади;
- список соревнований;
- структуру `соревнование → категория/класс → результаты`;
- связь результата со спортсменом и лошадью;
- минимальное создание и редактирование основных записей;
- понятную отметку, что это demo-прототип, а дополнительные функции появятся в
  следующих версиях.

База, Swagger, Prisma Studio, миграции, связи таблиц и техническая отладка
заказчику не показываются. Обучение операторов, загрузка Excel и эксплуатация с
реальными данными выполняются после подтверждения demo-MVP.

## 2. Рабочая установка

Это не публичный информационный сайт и не полный production-релиз.

Первый результат — защищённый демонстрационный интерфейс инструмента учёта,
работающий на подготовленных данных через существующий Admin API.

Архитектура первого показа:

```text
demo-web → NestJS Admin API → Prisma → PostgreSQL
```

Frontend никогда не подключается напрямую к PostgreSQL.

## 3. Масштаб и ограничения проекта

План исходит из следующих утверждённых условий:

- системой будут пользоваться 1–3 сотрудника;
- объём спортсменов, лошадей и соревнований небольшой;
- данные будут вводиться вручную или позднее загружаться через Excel;
- внешние автоматические источники не подключаются;
- высокой нагрузки и десятков одновременных редакторов не ожидается;
- текущие PostgreSQL, Prisma и NestJS достаточны;
- текущую Prisma-схему не нужно переписывать или физически сокращать;
- безопасность связей, защита от дублей и история изменений сохраняются;
- сложная enterprise-инфраструктура не требуется.

Не добавлять без отдельного доказанного блокера:

- микросервисы;
- Redis;
- Kafka или другую очередь;
- отдельный worker;
- полнотекстовый search engine;
- универсальный ETL;
- data warehouse;
- сложный approval workflow.

## 5. Сценарий демонстрации

Показ должен занимать 7–12 минут и идти по одному маршруту:

1. Войти в demo-контур или открыть заранее подготовленную сессию.
2. Открыть реестр спортсменов.
3. Найти спортсмена, применить фильтр и изменить сортировку.
4. Открыть карточку спортсмена и показать связанные результаты/лошадей.
5. Открыть реестр лошадей, найти запись и открыть карточку.
6. Открыть соревнования и выбрать одно соревнование.
7. Показать его категории/классы.
8. Выбрать класс и показать таблицу результатов.
9. Открыть один результат и показать связь спортсмен + лошадь.
10. Изменить одно безопасное demo-поле и показать обновление таблицы.
11. Показать отметку «Демо-прототип» и краткий список будущих возможностей.

Во время показа не открывать:

- SQL и структуру таблиц;
- Swagger/OpenAPI;
- Prisma Studio;
- логи;
- терминал;
- экран миграций;
- технические настройки безопасности;
- незавершённые функции.

## 8. Решение по категориям соревнований

Текущая структура уже поддерживает требуемую иерархию:

```text
CompetitionEvent
└── CompetitionClass
    ├── discipline
    ├── category
    ├── level
    └── CompetitionResult[]
```

Для demo:

- соревнование является контейнером;
- `CompetitionClass.category` используется как категория;
- `CompetitionClass.level` используется как уровень;
- `sortOrder` определяет порядок категорий/классов;
- frontend группирует или переключает классы по `category`;
- результаты фильтруются по выбранному классу.

Отдельную таблицу `CompetitionCategory` не создавать, пока Федерация не
утвердила обязательный справочник, иерархию и правила переиспользования
категорий между соревнованиями.

В demo seed использовать небольшой согласованный набор категорий. Эти значения
должны быть явно помечены как демонстрационные, если они не утверждены FEM.

## 9. Что означает «БД готова к frontend»

Готовность не означает завершение всей базы. Gate считается пройденным, когда:

1. Миграции применяются к чистой PostgreSQL 16.
2. Prisma schema валидна, Prisma Client генерируется.
3. Demo seed повторяем и не создаёт дублей.
4. Есть связанные спортсмены, лошади, соревнования, классы и результаты.
5. Основные FK и ограничения не позволяют создать разорванный результат.
6. Списочные Admin API возвращают стабильную пагинацию.
7. Все нужные фильтры и сортировки имеют allowlist.
8. Detail API возвращают связи, необходимые карточкам.
9. Таблицы получают человекочитаемые значения, а не только UUID.
10. Основные create/update операции проходят в demo-контуре.
11. Ошибки имеют безопасный формат и `requestId`.
12. OpenAPI соответствует runtime.
13. Backend tests для demo-контура проходят.
14. Frontend не требует ручных SQL-запросов или Prisma Studio.

## 12. Требования к интерфейсу

- основной demo-режим — desktop 1280 px и выше;
- интерфейс не ломается на tablet и узком desktop;
- mobile должен оставаться доступным, но отдельная mobile-концепция не блокирует
  demo;
- таблицы остаются семантическими таблицами;
- на узком экране допускается горизонтальный scroll и приоритетные колонки;
- сортировка отражается визуально и через `aria-sort`;
- фильтры можно сбросить;
- pagination/filter/sort state сохраняется в URL;
- «нет данных» отличается от «фильтры ничего не нашли»;
- raw backend messages не выводятся пользователю;
- UUID, `version`, `isDemo`, timestamps аудита и технические поля скрыты;
- состояние demo обозначается в header и в данных;
- будущие возможности описываются в одном информационном блоке;
- не добавлять неработающие пункты меню и fake buttons;
- используются правила `docs/design-constitution.md`;
- критические действия ждут подтверждения backend.

## 13. Demo-данные

Минимальный набор:

- 12–20 спортсменов;
- 12–20 лошадей;
- 3–5 клубов;
- 2–4 дисциплины;
- 3 соревнования;
- 3–6 классов на соревнование;
- 3–5 демонстрационных категорий;
- 40–80 связанных результатов;
- статусы finish/withdrawn/disqualified или их утверждённые аналоги.

Требования:

- имена реалистичны, но данные явно вымышленные, если FEM не подтвердила
  использование реальных;
- нет записей вида `Demo Rider 01`;
- все ключевые отношения заполнены;
- есть длинные значения, пустые необязательные поля и разные статусы;
- повторный seed не создаёт дубли;
- demo-контур нельзя смешать с реальными данными.

## 15. Критерии готовности demo-MVP

Demo можно показывать, если:

- используется отдельная demo-БД;
- интерфейс явно помечен как demo-прототип;
- доступны только необходимые разделы;
- спортсмены ищутся, фильтруются, сортируются и открываются;
- лошади ищутся, фильтруются, сортируются и открываются;
- соревнования фильтруются и открываются;
- категории/классы видны внутри соревнования;
- результаты связаны со спортсменом и лошадью;
- минимум одна create/update операция безопасно работает;
- frontend общается только с API;
- UUID и внутренние поля не показываются;
- loading/empty/error/not-found реализованы;
- desktop demo не имеет критических дефектов;
- lint, typecheck, unit и build проходят;
- известные ограничения записаны;
- Swagger, SQL, Prisma Studio и терминал не нужны для показа.

Не блокируют demo:

- отсутствие Excel;
- отсутствие обучения;
- отсутствие публичного сайта;
- отсутствие рейтинга;
- отсутствие owners UI;
- отсутствие CMS;
- отсутствие dashboard;
- отсутствие второго языка;
- отсутствие полной mobile-оптимизации;
- отсутствие production SLA.
